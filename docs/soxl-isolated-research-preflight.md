# SOXL Isolated Research Preflight

This entrypoint reads an existing private input package for isolated development research. The default mode runs preflight only; explicit development mode runs backtests without calling external models, placing orders, promoting candidates, consuming prior candidate mandates, or modifying existing packages or ledgers.

Existing development aggregate results can be consumed offline using mutually exclusive `--completed-result <path> --completed-result-sha256 <sha256>`, which omits `--snapshot` and invokes no preflight, runner, or model. Output therefore sets `real_backtest_executed=false` and `completed_result_reused=true`, while a `true` flag in the original result remains a historical execution fact subject to validation. The entrypoint reads the file once to verify expected byte SHA-256 and JSON together, rejecting symlinks, non-regular files, empty files, and inputs above 1 MiB.

The CLI entrypoint is `scripts/preflight_soxl_isolated_research.py`, calling `lifecycle.soxl_isolated_research.preflight_soxl_isolated_research`. Callers must supply the approved directory, package manifest SHA-256, and input manifest SHA-256; the entrypoint never scans to pick inputs or self-trusts freshly computed digests.

```text
python scripts/preflight_soxl_isolated_research.py \
  --snapshot <approved-private-snapshot-dir> \
  --package-sha256 <approved-package-root> \
  --input-manifest-sha256 <approved-input-root>
```

Preflight enforces the original four-file layout and `0700`/`0600` permissions, rejects symlinks, verifies member bytes and lengths, and checks original source retention deadlines using UTC time. The source must remain `provider_observed` with encrypted local internal-research retention; synthetic data, proxy substitutions, and relaxed retention scopes are rejected. Pure `prepare_soxl_pit_input` re-verifies source, calendar, listing availability, and prefix provenance in memory against canonical bytes without calling `publish_soxl_pit_input` or writing bars or receipts to disk. Package and source identities retain their creation-time UES (`<pinned-commit-sha>`) and QPK (`<pinned-commit-sha>`) revisions rather than rewriting them to consumer versions.

The sole parameter is `trend_entry_buffer`, bounded to `0.08`–`0.12` (default `0.08 / 0.10 / 0.12`). The `0.08` baseline must be present and counted; values must be strictly ascending with at most 25 entries. Runtime configs derive independently from consumer UES (`<pinned-commit-sha>`) and QPK (`<pinned-commit-sha>`) without overwriting source lineage. The parameter participates in strategy logic: when SOXX price exceeds the 140-day trend moving average times `(1 + trend_entry_buffer)`, the top trend tier activates. It does not alter position weights, stops, risk budgets, or mandates, and raising the threshold implies no proven return or risk gain.

Python returns the original `input_path`, `input_manifest_path`, source identity, and isolated full `runtime_configs` for downstream runners. The CLI emits only status, counts, Codex channel metadata, and research-authority flags—never paths, source dates, bars, raw exceptions, or full configs. Every config sets `learning_only`, `promotion_eligible=false`, `live_ready=false`, `size_zero_required=true`, and `no_order=true`; the list cap does not override the 25-trial cumulative execution cap.

By default the CLI runs preflight only. With `--run-development`, it re-runs the full input gate and binds a second read of `input.json` bytes to the package's verified member SHA-256, aborting before orchestration if the file changes between reads. It then runs the three parameter trials sequentially through `BacktestOrchestrator.run` with an in-memory no-write sink. Each trial computes fixed `5 / 10 / 15 bps` cost scenarios; fees are fixed scenarios, not tunable parameters. The window spans from the first session through the end of the prior WFA window and is labeled `seen_development`. Integrity checks still read the whole package, while computation and tuning exclude the subsequent prior locked OOS window.

The learning adapter exposes only standard `run` without promotion-runner folds or locked-OOS methods. It reuses validated lot accounting, cash handling, half-L1 costs, open-gap stops, same-day low stops, close decisions, and metrics; per-prefix indicators are cached per job index and copied before passing to the strategy, without writing to disk or exposing future sessions. Strategy decisions use the pinned UES pure builder rather than standard decision records or promotion authority. Existing `0.01` simulated loss budget, `5%` executable stop, `0.50` effective exposure, `3x` SOXL factor with `0.15` notional cap, `5%` drawdown halving, `10%` account breaker, and `3`-stop parking remain active. `RiskEngine.assess` acts as an additional sanity check: close decisions consume its approval scalar (rejecting errors, non-finite values, or scalars > 1), and open-stop assessments use current-day open valuation and prior-session regime, failing closed if scalar < 1. It creates no evidence or authority.

Development output contains only per-trial/cost-scenario aggregate return, risk, cost, turnover, fill, and assessment counts plus fixed research boundaries. If a second or later cost scenario fails, execution stops immediately, preserves completed aggregates, and reports separate started and completed trial/scenario counts. Status uses `development_completed` or `development_incomplete` only—never `PASS`, `ready`, `promotion`, or shadow claims. Legacy `_validate_config` / `_require_run_contract` continue binding the prior candidate without overwriting its identity, consuming its ledger, or relabeling the development window as fresh OOS. Promotion and forward evidence for a new candidate still require separate generation.

Completed-result mode accepts only complete, flag-consistent trial payloads with valid comparisons: values must be strictly ascending and include the `0.08` baseline, each trial must include `5 / 10 / 15 bps` scenarios, started/completed counts must match contents, and all aggregates must be finite non-boolean numbers. When all parameter trials yield identical aggregates at each fee tier, output sets `status=completed`, `outcome=no_improvement`, and returns a QPK `OptimizationProposal(recommendation="hold")` for the isolated learning profile with both current and proposed values at `0.08` and unattached to the production strategy identity. Any aggregate difference sets `outcome=requires_review` without proposing a parameter change, keeping `promotion_eligible=false` and `walk_forward_passed=false`, without labeling `seen_development` as OOS or claiming automated task, production drift, or job bindings.

Verification uses generated synthetic market fixtures, an isolated interpreter, and network blocking. Running on real private inputs requires separate explicit authorization and is not proven by synthetic unit tests.
